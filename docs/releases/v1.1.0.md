## What's in 1.1.0

**KiviDB is now open source,** under the GNU Affero General Public License,
version 3 (AGPL-3.0-only). The KiviDB End User License Agreement no longer
applies to this or later releases. Using KiviDB as the database of your
application does not put your application under the AGPL; only a modified
KiviDB offered to others over a network must have its source offered too.
A commercial license is also available. The entitlement check that builds for cloud
marketplaces made at startup is removed, with the marketplace machine images.

1.1.0 supersedes 1.0.6, which was published only as release candidates
(1.0.6-rc1 to 1.0.6-rc4) and never as a final release. Everything in those
candidates is in 1.1.0. Coming from 1.0.5, it brings:

- security fixes: Lua scripts are kept in their sandbox, a command a script
  calls is checked against the user's ACL, protected mode is enforced, and
  malformed input from a client can no longer crash or stall the server;
- a server log you can act on, and a page explaining every warning and
  error;
- a startup update check;
- cluster work: `min-replicas-to-write`, hostnames, a bus secret, TLS
  between nodes, and search indexes and queries across every master;
- lower memory per key, scripts that run several times faster, and vector
  ingest about six times faster;
- images on Docker Hub as well as GHCR.

[CHANGELOG.md](https://github.com/kividbio/kividb/blob/master/CHANGELOG.md)
has the full list.

## Before you upgrade

- **Protected mode is now enforced** (`protected-mode yes`, the default, as
  in Redis). With no `bind` address given and no password on the `default`
  user, only clients on the same machine may connect; others are told
  `-DENIED` and disconnected. It used to be ignored. A server reached over
  the network with a passwordless `default` user needs a password, a `bind`
  address, or `protected-mode no`. Replicas and cluster nodes connect as
  clients too. The Docker image turns protected mode off unless you pass
  arguments of your own.
- **Scripts are checked against the caller's ACL.** A command a script runs
  through `redis.call` is now held to the same ACL rules as one the user
  sends directly. A user allowed `EVAL` could previously run any command on
  any key from a script.
- **Scripts lose `package`, `require`, `loadfile`, `dofile`, `debug` and
  `string.dump`, and `load` takes source text only**, not bytecode. A script
  that used any of these fails.
- **Scripts on one hash tag may not touch keys outside it.** A script whose
  `KEYS` all carry one hash tag (`{orders}:waiting`) now runs beside scripts
  on other tags, and a `redis.call` on a key outside its tag fails.
  `lua-parallel-scripts no` restores the old behaviour. See
  [docs/SCRIPTS.md](https://github.com/kividbio/kividb/blob/master/docs/SCRIPTS.md).
- **`tls-ca-cert-file` now verifies client certificates.** It was read and
  then ignored, so any client that trusted the server could connect. With a
  CA file set, a client must now present a certificate that CA signed, as on
  Redis. If you set `tls-ca-cert-file` and your clients send no certificate,
  they will be refused after upgrading: give them certificates, or set the
  new `tls-auth-clients` to `no` (not asked) or `optional` (checked only when
  presented). Without a CA file nothing changes.
- **The server now makes one outbound HTTPS request at startup** to
  `https://github.com/kividbio/kividb/releases/latest`, unless you turn it off. If your
  hosts may not reach the internet, or you do not want the request made,
  add `update-check no` to the config file (or pass `--update-check no`, or
  set `KIVIDB_NO_UPDATE_CHECK=1`). A host without internet access still
  starts; it waits at most 1.5 seconds for the reply, and the failure is
  logged at debug level only.
- **`loglevel` now works.** It was accepted and ignored: every message was
  printed, whatever it was set to. If you start KiviDB with `--loglevel
  warning` or `error`, the informational lines (loading, saving, role
  changes) are no longer printed. The default, `notice`, shows them.
- **Log lines changed shape.** Each now starts with a UTC timestamp and the
  process id: `2026-10-09T07:21:30.114Z 4242 [INFO] …`. Lines that were
  tagged `[AOF]`, `[REPL]` or `[CLUSTER]` are now `[INFO]`, `[WARN]` or
  `[ERROR]` lines that begin `AOF:`, `Replication:` or `Cluster:`. If you
  parse the log, check your patterns; or switch to `log-format json`.
- **The arm64 Linux binary, packages and image need an ARMv8.1 CPU**
  (Graviton2 and later, Ampere, and other current arm64 servers). A
  Raspberry Pi 4 and a first-generation Graviton can no longer run them.

## Added

- **Logging you can act on.** See
  [docs/LOGGING.md](https://github.com/kividbio/kividb/blob/master/docs/LOGGING.md)
  and [docs/ERRORS.md](https://github.com/kividbio/kividb/blob/master/docs/ERRORS.md).
  - Redis's levels: `debug`, `verbose`, `notice` (the default), `warning`
    and `nothing`. `CONFIG SET loglevel` changes it at runtime. `CONFIG SET
    loglevel verbose` and `notice` used to be refused, though the error
    message listed them.
  - `logfile` writes the log to a file. It used to be accepted and ignored.
  - `log-format json`: one JSON object per line, for log pipelines.
  - New lines: `Ready to accept connections on …` once the server is
    listening; the version, pid and config file at startup; every
    `CONFIG SET` (secrets hidden); memory full and writes refused with
    `OOM`; a script past `lua-time-limit` making other clients wait. At
    `verbose`: every client connection and disconnection, failed
    authentication, and protocol errors.
  - Warnings and errors say what to do. Some that did not now do: a port in
    use, a failed background save (which used to print a Rust debug dump), a
    failed save at shutdown, an unreadable ACL file, io_uring blocked by a
    seccomp profile, a full disk or failing fsync under the AOF, and running
    out of file descriptors.
  - Errors that can repeat as fast as the work behind them (every AOF write
    on a full disk, every accept at the file-descriptor limit) are logged at
    most every 10 seconds.
  - [docs/ERRORS.md](https://github.com/kividbio/kividb/blob/master/docs/ERRORS.md)
    explains every `[FATAL]`, `[ERROR]` and `[WARN]` line, and every error
    reply a client can get (`OOM`, `BUSY`, `NOSCRIPT`, `CROSSSLOT`, …): what
    it means, how urgent it is, and what to do.

- **Startup update check.** Once per start, KiviDB asks this repository's
  GitHub releases page whether a newer release is out. If one is, the first
  thing it prints, above the banner, is a notice with the link to it.
  - It requests `https://github.com/kividbio/kividb/releases/latest` and
    reads the newest release's tag from GitHub's redirect. No API, no
    token, no rate limit. Nothing is sent but the request itself: no host
    name, configuration, key or dataset information, and no identifier.
  - Startup waits for the reply at most 1.5 seconds; a slower reply is
    dropped. It never touches client connections.
  - Only a version-shaped tag (`v1.2.3`, `v1.2.3-rc1`) is accepted, and
    nothing else from the reply is printed.
  - It is never made by debug builds, or when `CI` is set.
  - `update-check-url` points it at another HTTPS address, such as a mirror
    in a closed network.

  See [docs/UPDATE_CHECK.md](https://github.com/kividbio/kividb/blob/master/docs/UPDATE_CHECK.md).

- **Cluster:** `min-replicas-to-write` and `min-replicas-max-lag`, as in
  Redis; `INFO cluster`; `cluster-announce-hostname` and
  `cluster-preferred-endpoint-type`; `cluster-bus-secret`, which a node must
  prove it knows before anything it sends on the cluster bus is read; and
  TLS between nodes with `tls-cluster` and `tls-replication` (builds with
  TLS).
- **Cluster: search across every master.** `FT.CREATE`, `FT.ALTER`,
  `FT.DROPINDEX` and the other index-definition commands reach every
  master, and `FT.SEARCH`, `FT.AGGREGATE`, `FT.INFO` and `FT.TAGVALS` sent to
  any node are answered from the whole cluster. If a master cannot answer,
  the search fails rather than answer from part of the data.
- **A restarted master continues its replicas** instead of sending them the
  whole dataset again: after a clean `SHUTDOWN` with the AOF on, and after
  `kill -9` or a crash when a replica holds the same data.

## Fixed

- **`REPLICAOF NO ONE` during a full sync lost the promoted node's data.**
  A replica promoted while a full-sync payload was still arriving read the
  rest of it, dropped its own dataset and loaded the old master's, and only
  then stopped replicating. The sync now stops at once and the node keeps
  its dataset; a promotion that arrives while the dataset is being replaced
  waits for that to finish, as on Redis. Found in a failover test of
  1.1.0-rc1.
- **A transaction or a script could wait for ever.** A thread that ran its
  first command while a transaction or script was starting did not queue
  behind it. A few such threads running command after command could keep it
  waiting indefinitely, and every transaction and script after it queued
  behind it. It now makes those threads wait too once it has waited 2 ms.
- **Lua scripts could leave the sandbox**, load native code and run
  commands on the host (see *Before you upgrade*).
- **Malformed input could crash or stall the server.** Counts that overflow,
  `RESTORE` payloads that ask for more memory than they hold, `BITFIELD`
  offsets past 2^32, and deeply nested input to `cmsgpack.unpack`, search
  queries and JSONPath filters are now refused. A client that has not
  authenticated is held to Redis's request limits.
- **TLS client certificates were never verified** (see *Before you
  upgrade*). New `tls-auth-clients`: `yes` (the default, as on Redis),
  `optional` or `no`.
- **Lua: every status reply reaches a script as an `{ok = ...}` table**, as
  in Redis, not only `+OK`. `PING`'s `+PONG` and `TYPE`'s `+set` came back as
  plain strings, so scripts reading `.ok` got `nil`. In BullMQ that broke
  dependency pagination, and made `removeOrphanedJobs` delete live jobs: 21
  tests of BullMQ's suite failed on 1.0.5 for this reason
  (`scripts/client_compat/` runs it).
- A port already in use crashed the server with a panic on the io_uring
  path; it is now a `[FATAL]` line that says what to do.
- **A second server on a port in use no longer shares it.** On Linux the
  io_uring workers share their port (`SO_REUSEPORT`), so a second KiviDB
  started on the same port by mistake came up "ready" and took a share of
  the first one's clients. It now refuses to start.
- **Cluster: a slot migration or a manual failover could lose one
  acknowledged write.** A write that slipped in between "pause writes" and
  the handover was applied on the old owner, acknowledged, and never reached
  the new one. It now waits for the handover and is redirected. This was in
  1.0.5 as well: the test for it failed about 1 run in 25, and passes 100
  of 100 now.
- **An AOF rewrite stopped every read and write for as long as it took.**
  Writes are now held only while the dataset is captured: with about 9
  million keys, under 100 ms.
- **Cluster:** a manual failover could time out with every vote given; a
  key moved by `RESTORE`, `MIGRATE` or slot migration was in no search
  index; `redis-cli --cluster reshard` onto a new node could leave the
  cluster disagreeing; and a cluster restarted as a whole could fail over
  nodes that were only starting. See the changelog for these and the other
  cluster fixes.
- **A time to live could end a millisecond early**, and `PTTL` straight
  after `SET k v PX 250` said 249.
- **`MSET`, `MSETNX` and `MGET` are each one step.** A reader could see half
  an `MSET`.
- **A hash returns its fields in the order they were set**, as Redis does
  for small hashes.
- With these, **BullMQ 6.3.11's own test suite passes in full on KiviDB**
  (944 tests, and 163 in its ioredis configuration), as does Sidekiq
  8.1.7's (749). Both libraries' soak tests pass too, including with the
  server killed and restarted mid-run: no job lost, none run twice.
  `scripts/client_compat/` runs them.
- **AOF: a server killed in the middle of a script could restart with half
  of that script's writes.** Each write a script made went to the AOF as its
  own record. They now go together, so a script is one step in the log as it
  is to clients. In a test that kills the server under load, 2 kills in 40
  left a script half applied before, and none in 40 now.
- `CONFIG SET loglevel verbose` and `notice` were refused, though the error
  listed them as valid.
- **`SSCAN`, `HSCAN` and `ZSCAN` return a small collection whole**, cursor
  0, whatever `COUNT` says, as Redis does for anything small enough for its
  compact encodings (`OBJECT ENCODING` says `listpack` or `intset`). They
  used to page it.
- **`MAXLEN ~` trims as close as Redis does with large entries.** A stream
  node now ends at `stream-node-max-bytes` (4096, and now a real setting) as
  well as at 100 entries. With 200-byte entries, `MAXLEN ~ 20` kept 100; it
  keeps 22 (Redis: 26).
- `BACKUP CLEANUP` removes only the backup's own files from
  `backupdirname`, not everything in it.

## Faster and smaller

- **Vector ingest is about six times faster.** Each HNSW node has its own
  lock, so inserts no longer wait for one another: 1.18 million vectors
  (glove-25-angular, `M 16`, `EF_CONSTRUCTION 256`, 100 clients) took 197 s
  and take 31 s on a 64-core server, where Redis 8.10 takes 38 s.
- **Lua scripts run several times faster.** With 50 clients running a short
  script, KiviDB did about 10,500 a second and now does 36,000 to 42,000
  (local Docker; Redis 8 on the same machine does 141,000). The median reply
  went from 3.9 ms to about 1.2 ms. BullMQ runs nearly everything as a
  script: a soak of 5,400 jobs that took 18.5 s on 1.0.5 takes 4.5 s, about
  what it takes on Redis.
  - A script is compiled once and kept, as Redis keeps it. It used to be
    compiled on every call.
  - A script that has run in under a millisecond is run where it arrives,
    rather than handed to another thread and back. One that later takes over
    5 ms goes back to being handed off, so a slow script still cannot hold
    up the connections that share its thread.
  - When several clients run quick scripts at once, one thread runs them
    back to back.
  - Scripts whose keys share one hash tag run in parallel with scripts on
    other tags.
- **Memory per key is lower.** Ten million keys of 16 bytes with 100-byte
  values take 177 bytes a key where they took 217.
- **Connections are spread evenly over the io_uring workers.**
- `SPOP`, `SRANDMEMBER`, `ZRANGE` by index and `ZRANGEBYSCORE` no longer
  walk or copy the whole collection.

## Changed

- **Images are on Docker Hub as `kividb/kividb`**, as well as on GHCR as
  `ghcr.io/kividbio/kividb`, with the same tags. They are no longer
  published to Quay, and the release binaries are downloaded from GitHub
  Releases rather than `releases.kividb.io`.
- **Licensing.** KiviDB is licensed under the GNU Affero General Public
  License, version 3. The startup banner says so.
- The default and `-lua` builds now include a TLS client (rustls, with
  compiled-in root certificates) for the update check, which makes them
  about 3.8 MB larger.
- **`CONFIG REWRITE` writes the settings in effect**, `CONFIG SET` changes
  included.
- `CONFIG GET loglevel` answers with Redis's level names (`notice` rather
  than `info`).

## Known limitations

- **A hard kill can lose the last acknowledged writes, with the AOF on.** A
  write is answered when its record is queued for the append-only file, not
  when it has been written to it. If the process is killed outright
  (`kill -9`, the OOM killer), the writes of the last fraction of a
  millisecond may not be in the file; in testing that was up to four
  writes. A normal shutdown loses nothing.
- **Cluster: `FT.SPELLCHECK`, `FT.PROFILE`, `FT.HYBRID` and `FT.SYNDUMP`
  answer from the node they are sent to.**
- **Cluster: without `tls-cluster`, what nodes send each other is in the
  clear**, as in Redis; `cluster-bus-secret` only keeps strangers off the
  bus.
