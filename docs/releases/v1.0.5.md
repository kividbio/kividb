## What's in 1.0.5

KiviDB 1.0.5 brings the server up to **Redis 8.10**: the commands Redis
added in 8.4, 8.6, 8.8 and 8.10, Redis's own replies and error messages,
and the behaviour Redis's test suite checks for. Measured with that suite
(Redis 8.0.0, one unit at a time), 1.0.4 passed 648 tests and 1.0.5 passes
1,892, with 31 failing.

It also fixes eleven engine issues found by testing 1.0.4 under a
Kubernetes operator, the eight search issues found running LiteLLM's semantic cache on
RedisVL, and a long list of replication, clustering and data-loss bugs. Some
of those bugs could lose or corrupt data; they are listed under *Fixed*.

**Read *Before you upgrade* first.** Some changes need you to act, and many
replies and error messages now follow Redis, so a client that matched on
KiviDB's old wording may notice.

## Before you upgrade

- **Re-add geo data.** Positions are now stored in Redis's encoding. A geo
  key written by 1.0.4 or earlier is read back at the wrong coordinates, and
  nothing can tell an old score from a new one. Delete each geo key and
  `GEOADD` its members again after upgrading.
- **Check your ACL file and config file.** Both are now read strictly. A
  rule or directive the server does not understand stops startup (and fails
  `ACL LOAD`) with the line number, where it used to be skipped. `ACL LOAD`
  now leaves exactly the users in the file. `ACL SETUSER` and `ACL DELUSER`
  no longer write the file; `ACL SAVE` does.
- **Check users that rely on patterns or categories.**
  - Key patterns (including `%R~` / `%W~`) and channel patterns (`&`) are
    enforced. A user with no channel pattern can no longer publish or
    subscribe.
  - `-@dangerous` and `-@admin` now deny commands; they used to be accepted
    and ignored.
- **A persistence file that cannot be read stops the server.** It used to be
  skipped, and the server started empty. An AOF cut short by a crash is
  trimmed to its last whole command and loaded.
- **`maxmemory` is measured against allocated memory** (`used_memory`), not
  the resident set size. All of Redis's eviction policies are implemented.
  A limit below current usage now evicts or refuses writes, where before it
  might not have triggered.
- **Builds without TLS refuse `--tls-port`.** The plain and `-lua` binaries
  and images exit at startup if given a TLS port, instead of serving
  plaintext. Use a `-tls` or `-full` build for TLS.
- **RESP2 client-side caching needs `REDIRECT`.** A RESP2 connection that
  enables `CLIENT TRACKING` without it is now sent nothing, as in Redis. Use
  `HELLO 3`, or redirect to a connection subscribed to
  `__redis__:invalidate`.
- **`SCAN` cursors from 1.0.4 are not valid.** Finish or restart any
  long-running scan across the upgrade.

## Behaviour that changed

These follow Redis. Most clients will not notice; ones that compare error
text, or rely on what KiviDB used to accept, may.

- **Errors are Redis's.** The wrong number of arguments is refused before
  anything else (`ERR wrong number of arguments for 'get' command`), and an
  unknown command reads `ERR unknown command 'x', with args beginning with:
  …`. Inside `MULTI`, either one aborts the transaction (`EXECABORT`).
- **A malformed request closes the connection** with `-ERR Protocol error:
  …`: a length that is not a number, an argument over 512 MB, a line over
  64 KB, unbalanced quotes. Such a connection used to wait for ever.
- **`CONFIG SET` is all or nothing.** An unknown parameter, a value out of
  range, or one that cannot change at run time is an error that names it,
  and none of the pairs given with it is applied.
- **`CLIENT PAUSE … ALL` pauses reads too.** `WRITE` holds everything that
  may write: `PFCOUNT`, `PUBLISH`, scripts not declared `no-writes`, and an
  `EXEC` containing any of them.
- **Transactions and scripts run alone.** Other clients wait for a running
  script and are told `BUSY` only after `lua-time-limit`.
- **Functions are held to their flags.**
  - `FCALL_RO` refuses a function not registered with `no-writes`.
  - At the memory limit, a function runs only if it has `allow-oom` or
    `no-writes`.
  - A library loads with only `redis.register_function`, `redis.log` and the
    version constants in reach, and cannot set globals.
  - Library names are case-sensitive.
- **A key that loses its last element is deleted** — lists, sets, sorted
  sets, hashes and vector sets. It used to stay behind as an empty key.
- **JSON** answers once per match for a `$` path, keeps object members in
  insertion order, and returns `[]` rather than nil when nothing matches.
- **Search** returns what was asked for (`RETURN`, `LOAD`) rather than every
  field. Malformed queries and unknown arguments are errors.
- **Pub/Sub:** a subscriber that falls too far behind is disconnected rather
  than silently skipping messages.
- **Replicas:** a replica drops its dataset before loading a full sync,
  needing memory for one dataset rather than two
  (`repl-diskless-load swapdb` restores the old behaviour). It refuses a
  full resync from an empty master while it holds data.
- **Smaller changes:**
  - `EXPIRE … GT` on a key without a TTL does nothing.
  - `ZADD` compares scores exactly.
  - `RANDOMKEY` is random.
  - `DIGEST` is XXH3-64.
  - `OBJECT ENCODING` names Redis's encodings.
  - `CLIENT LIST` uses Redis's layout and field names.
  - `INFO` reports `redis_version:8.10.0`.

The changelog lists every change.

## New

**Redis 8.4 – 8.10 commands**

- **8.4:** `DIGEST`, `DELEX`, `SET … IFEQ | IFNE | IFDEQ | IFDNE`;
  `XREADGROUP … CLAIM`; atomic slot migration (`CLUSTER MIGRATION`).
- **8.6:** idempotent `XADD` (`IDMP`, `IDMPAUTO`, `XCFGSET`); `HOTKEYS`;
  time-series `NaN` with `COUNTNAN` / `COUNTALL`.
- **8.8:** `AGGREGATE COUNT` for sorted sets; `JSON.SET … FPHA`; several
  aggregators per `TS.RANGE`; slow-log argument limits.
- **8.10:** `LMOVEM` / `BLMOVEM`; `SUNIONCARD` / `SDIFFCARD`; `HIMPORT`;
  `BACKUP`; `MAXCOUNT` / `MAXSIZE` for `XREAD` / `XREADGROUP`;
  `FT.ALIASLIST`; `TS.NRANGE`, `TS.READ`, `TS.QUERYLABELS`; the JSONPath
  extensions.

**Replication and clustering**

- **Partial resynchronisation:** a replication backlog
  (`repl-backlog-size`, `repl-backlog-ttl`) and `PSYNC`. A replica that
  reconnects, or restarts cleanly, continues where it was instead of
  copying the whole dataset again.
- **Options:** `masterauth`, `masteruser`, `repl-timeout`,
  `repl-ping-replica-period`, `replica-full-sync-guard`,
  `repl-diskless-load`, and the `cluster-announce-*` family.
- **`COMMAND`** now describes every command — arity, key specifications,
  flags — so cluster-aware clients such as redis-py's can route commands.

**Memory**

- Every Redis eviction policy, with `maxmemory-samples`, `lfu-log-factor`,
  `lfu-decay-time`, `OBJECT IDLETIME` / `OBJECT FREQ` and the `evicted`
  event.

**Search and JSON**

- A full JSONPath engine.
- Indexes `ON JSON`.
- `FT.AGGREGATE … WITHCURSOR` and the 8.8 reducers.
- `FT.EXPLAIN`, `FT.PROFILE`, `VECTOR_RANGE`, `HIGHLIGHT`, `INKEYS`.

**Clients and introspection**

- **Client-side caching:** `BCAST`, `PREFIX`, `REDIRECT`, `OPTIN` /
  `OPTOUT` / `NOLOOP`; every key a command reads is tracked.
- **`CLIENT`:** every `CLIENT LIST` / `CLIENT KILL` filter;
  `CLIENT REPLY`, `NO-EVICT`, `NO-TOUCH`.
- **`MONITOR`** on an ordinary connection.
- **Introspection:** `LATENCY HISTOGRAM`; `XINFO STREAM … FULL`;
  `SCAN … TYPE`, `HSCAN … NOVALUES`, `ZSCAN … NOSCORES`.

**ACL**

- New categories, including `admin`, `dangerous`, `blocking`, `fast`,
  `slow` and `transaction`.
- Rules for a single subcommand (`+config|get`, `-client|kill`).

## Fixed

These are the fixes that could lose data, corrupt it, or hang a client.
There are many more in the changelog.

**Replication and persistence**

- **Full resync:** one that was cut off left the replica with no keys, and
  a master restarting in a loop did that to every replica at once.
- **Write order:** concurrent writes to one key could reach replicas and the
  AOF in a different order than the master applied them.
- **Databases:** writes could reach the wrong database on a replica, in the
  AOF, or in a backup, when clients wrote to several databases at once.
- **Blocked pops:** blocked list and sorted-set pops could return the wrong
  element and leave replicas with different data.
- **Relative TTLs** started over on AOF replay and expired late on replicas.
- **Shutdown:** the final snapshot on `SIGTERM` was sometimes not written.
- **AOF over `maxmemory`:** a server with AOF on and a dataset over
  `maxmemory` started empty, refusing every write in its own log.

**Correctness**

- **`COPY`** of a list, set, hash, sorted set or stream shared the value
  with its source: a write to either changed both.
- **`WATCH`:** two transactions watching one key could both succeed (a
  stock of five sold six).
- **Multi-key blocking:** a client blocked on several keys could take an
  element meant for a client that had waited longer, leaving that client
  blocked on an empty list.
- **Pub/Sub** lost messages for a subscriber more than 1024 behind.
- **Expiry:** keys could outlive their TTL by up to 1.6 s.

**Hangs and crashes**

- **Malformed requests:** a request beginning `*3000000000` aborted the
  server, and other malformed requests left the connection waiting for
  ever.
- **Scripts:** a command arriving as a script started could wait for ever,
  even when it came from the client trying to `SCRIPT KILL` that script.
- **Error replies:** one could contain a line break, which desynchronised
  the client.

**Search, cluster and ACL**

- **Search:** `ON JSON` indexes indexed nothing; `VECTOR_RANGE`, negated
  pre-filters and `OR` across clauses matched nothing.
- **Cluster:**
  - Commands were routed by their first argument rather than their keys.
  - `MIGRATE` moved only strings.
  - `PUBLISH` did not reach other nodes.
  - A failed-over master that came back served its stale data.
- **ACL** changes did not reach clients that were already connected.

## Compatibility

Redis 8.0.0's test suite, run one unit at a time against a single server on
Linux with io_uring:

| | passed | failed | units that did not finish |
|---|---:|---:|---:|
| 1.0.4 | 648 | 103 | 18 |
| 1.0.5 | 1,892 | 31 | 1 |

Twenty-three of the thirty-six units that can run against an external
server pass completely. These are among the 31 that still fail:

- `INFO keysizes` histograms.
- Lazy-free counters.
- `RESTORE` of payloads produced by Redis itself (KiviDB's `DUMP` format is
  its own).
- Expiry continuing during `CLIENT PAUSE`.

[`docs/REDIS_TEST_SUITE.md`](https://github.com/kividbio/kividb/blob/v1.0.5/docs/REDIS_TEST_SUITE.md)
lists all 31 by cause.

## Performance

On CI's benchmark (memtier_benchmark, AWS Graviton3 c7gn.12xlarge,
`-c 5 --pipeline=10`), throughput is lower than 1.0.4's:

| | 1.0.4 | 1.0.5 | change |
|---|---:|---:|---:|
| Pipelined write | ~16.4M ops/s | ~13.5M ops/s | −18% |
| Pipelined read | ~19.9M ops/s | ~17.2M ops/s | −14% |
| Mixed 1:1 | ~18.8M ops/s | ~14.3M ops/s | −24% |

This is the cost of the correctness work above:

- running transactions and scripts alone;
- ordering writes for replication;
- counting allocated memory;
- checking arity before every command;
- keeping per-command statistics.

1.0.5 remains several times faster than Dragonfly and Redis on the same
benchmark. Without pipelining the difference is not measurable.

## Known limitations

- **`EXEC` and scripts:** an `EXEC` that arrives just as a script starts
  still waits for the script to end rather than being told `BUSY`.
- **Flaky blocking test:** "Circular BRPOPLPUSH" fails in about one run in
  four on io_uring. A command arriving between two chained blocked moves can
  see the element part-way round.
- **Not implemented:** stemming and phonetic search; `GEO` / `GEOSHAPE`
  search fields; enforced query `TIMEOUT`; `tls-cluster`.
  [`docs/REDIS_8_4_TO_8_10_PARITY.md`](https://github.com/kividbio/kividb/blob/v1.0.5/docs/REDIS_8_4_TO_8_10_PARITY.md)
  has the full list.

## Since 1.0.5-rc1

No engine changes. Two fixes to release and benchmark tooling:

- The post-release container smoke test no longer starts the non-TLS
  images with a TLS port, which they now refuse. It also checks that they
  refuse it, and is limited to 20 minutes.
- The AWS benchmark instances install the current GitHub Actions runner.
  The create step also fails within 20 minutes if the runner does not
  register, instead of leaving the run queued.
