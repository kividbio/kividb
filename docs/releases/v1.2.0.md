## What's in 1.2.0

1.2.0 is mostly about **not losing writes, and being a better Redis**:

- **Durability.**
  - With the append-only file on, a write is now acknowledged only once its record is in the file, as in Redis, so a killed process keeps every write it acknowledged, as long as the disk keeps up: a reply waits at most 5 s for its record, and one sent without it is counted in `INFO persistence` as `aof_acks_before_write`.
  - A checkpoint no longer stalls writes for seconds on a slow disk.
  - A graceful shutdown (`SHUTDOWN`, SIGTERM) keeps every write it acknowledged: no command runs from the start of the final snapshot to the exit.
  - A transaction, or a script that writes more than once, reaches replicas and the AOF as one step, so a replica never shows it half done.
  - A manual failover whose election is slow no longer loses writes.
  - Automatic failover elects the replica with the most data, and a replica stands only once it holds its master's data: never in the middle of a full sync, and its data's age counts from when it was last in step.
  - A clean shutdown waits up to `shutdown-timeout` (10 s) for its replicas to have every write, so after a restart they carry on instead of being sent the whole dataset. A manual failover does the same for the master it replaces.
  - A full sync under heavy writes finishes: while the replica loads the dataset, the writes kept for it may grow to `repl-replica-sync-max-backlog-bytes` (1 GiB) instead of the normal limit, and both limits can be changed with `CONFIG SET`.
  - A replica stopped in the middle of a full sync keeps its last good `dump.kdb` instead of saving the partial dataset over it.
  - A server started in a data directory another one is still using, as a replacement pod can be after a forced delete, waits for it to exit instead of loading what it was about to replace.
- **Clusters.**
  - The bus keeps one connection per peer.
  - Nodes can announce a separate client port (`cluster-announce-client-port`), for NodePorts and load balancers.
  - After a failover, the shard's other replicas carry on instead of resyncing in full.
  - An import cut short by a restart cleans up after itself.
  - `redis-cli --cluster reshard` runs to the end under writes: writes to the keys a `MIGRATE` is moving wait for it, as in Redis, instead of making it answer `TRYAGAIN`. `redis-cli --cluster fix` closes a reshard that stopped halfway, and no key is left on the wrong node: `CLUSTER DELSLOTS` works as in Redis, and `DEBUG DIGEST-VALUE` returns each value's digest.
- **TLS without restarts.**
  - Certificates, CAs and `tls-port` change with `CONFIG SET`.
  - A server can turn TLS on while it runs.
  - `port 0` runs a server on TLS only.
  - `tls-auth-clients-allowed-names` accepts only client certificates whose names match.
- **Memory.**
  - Active defrag gives memory freed by deletes back to the system, and is on by default.
  - String values take less memory.
- **Multi-key writes.** `MSET` and `MSETNX` of keys in many shards no longer queue behind each other: 3.4 times as many a second with 1,200 clients, and a lower tail.
- **Search.** TEXT fields are stemmed, as in Redis: `preferences` finds `prefer`. Scores come out as Redis's, and `SCORER` is honoured. `FT.SEARCH` and `FT.AGGREGATE` take a `TIMEOUT`, and the timeout is safe across a rolling upgrade. Synonyms work. Scores stay right after updates and deletes.
- **Compatibility.** Dozens of fixes bring KiviDB's replies, errors, `INFO` and `CLIENT LIST` fields, keyspace events, Lua scripting and vector-set scores closer to Redis 8.10.
- **Signed releases.** Every file and image carries a signed build attestation. Check one with `gh attestation verify <file> --repo kividbio/kividb`.

[CHANGELOG.md](https://github.com/kividbio/kividb/blob/master/CHANGELOG.md) has the full list.

## Security

1.2.0 fixes issues that let a user restricted by ACL read or overwrite keys outside their permissions, or read credentials. 1.1.x is affected too and gets no further release, so upgrade to 1.2.0. Thanks to [@Parikalp-Bhardwaj](https://github.com/Parikalp-Bhardwaj), who reported them privately.

- **ACL key permissions bypassed through `SORT` patterns and multi-`STORE` destinations** ([GHSA-6rw7-4fcr-r6j3](https://github.com/kividbio/kividb/security/advisories/GHSA-6rw7-4fcr-r6j3)):
  - **`SORT` patterns.** A user whose ACL names some keys could read any key's value, or any hash field, with `SORT`/`SORT_RO ... GET *` or `GET *->field`, and learn the order of other keys with `BY *`. Such patterns now need read access to every key, as in Redis.
  - **A second `STORE`.** `SORT` with two `STORE`s, and `GEORADIUS`/`GEORADIUSBYMEMBER` with two `STORE`/`STOREDIST`s, wrote to a key the ACL had not checked.
  - **`XREADGROUP`.** With a group or consumer named `STREAMS`, it read streams the ACL had not checked.
- **Credentials in `SLOWLOG`, `MONITOR` and the log** ([GHSA-c4xj-63wm-4jj9](https://github.com/kividbio/kividb/security/advisories/GHSA-c4xj-63wm-4jj9)):
  - **`SLOWLOG GET`.** A user allowed it could read the passwords set with `ACL SETUSER`, and the values of `requirepass`, `masterauth`, `primaryauth`, `cluster-bus-secret` and the TLS key passphrases set with `CONFIG SET`.
  - **`MONITOR`.** It showed `MIGRATE`'s `AUTH`/`AUTH2` credentials.
  - **The server log.** The INFO-level line for `CONFIG SET` printed `primaryauth` and the TLS client key passphrase.

  They are now shown as `(redacted)`.

Not a vulnerability in any stable release, but fixed before 1.2.0 shipped: a race in active defrag's choice of slabs, new in the 1.2.0 release candidates, could hand out the same block of memory twice. It was found and fixed by @Parikalp-Bhardwaj.

## Before you upgrade

- **Upgrade replicas before their master.** A 1.2.0 master sends transactions to its replicas wrapped in `MULTI`/`EXEC`.
  - A 1.1.x replica still applies their writes one by one, but logs two `ERR unknown command` warnings for each transaction.
  - A 1.2.0 replica of a 1.1.x master is fine.
  - The KiviDB Kubernetes operator already restarts a shard's replicas first and its master last.
- **No going back to 1.1.x once 1.2.0 has saved.** A snapshot holding a time series with compaction rules uses a format 1.1.x cannot read. Take a backup before you upgrade if you may need to go back.
- **With the AOF on, writes are slower.** Waiting for the record costs 20–28% of `SET`s a second with 50 clients, and under 10% with one client; reads cost nothing. `aof-ack-after-write no` gives 1.1.x's behaviour and speed back, at the cost of losing the last few acknowledged writes to a killed process.
- **Scripts: `pcall` and `assert` behave as in Redis.**
  - A script that read `e.err` from an error `pcall` caught finds the message in `e` itself now.
  - `assert` with a table as its message fails with `bad argument #2 to 'assert'`.
- **`CONFIG SET` refuses what it cannot set,** as Redis does. Unknown names, and settings that only take effect at startup, are now errors. Before, they replied `OK`. Settings that used to be ignored in the configuration file are now applied.
- **`SORT` with a `BY` or `GET` pattern needs read access to every key,** as in Redis. A user whose ACL names some keys gets `ERR GET option of SORT denied due to insufficient ACL permissions.` for `GET *` or `GET *->field`, and the same for a `BY` with a `*`. `GET #` and `BY nosort` still work.
- **`AUTH <password>` is refused when no password is set,** as in Redis. Before, it said `OK`.
- **Search scores changed, to Redis's.** A word now also finds its other forms (stemming), and `WITHSCORES` / `ADDSCORES` values are Redis 8.10's: a TAG clause adds to the score, a field's `WEIGHT` counts each occurrence instead of multiplying the score. A threshold set on the old scores needs adjusting. `VERBATIM` on a query, or `NOSTEM` on a field, keeps the old matching.
- **`VSIM` / `VLINKS` scores are Redis's,** from 0 to 1 as `(1 + cosine) / 2`. A threshold an application set on the old scores, which went from -1 to 1, needs adjusting.
- **`activedefrag` is now on by default.**
- **A clean shutdown pauses clients while its replicas catch up,** for at most `shutdown-timeout` seconds (10 by default; tens of milliseconds in our tests). `SHUTDOWN NOW` and `SHUTDOWN NOSAVE` don't wait.
- **`repl-backlog-size` is 64 MB by default,** not 1 MB as in Redis and 1.1.x, so that replicas carry on after their master restarts under heavy load: 1 MB is a fraction of a second at 100k writes a second, less than a replica takes to come back, and it was then sent the whole dataset. A master keeps the backlog only from its first replica's sync until `repl-backlog-ttl` (an hour) after its last replica has gone, so a server that never has a replica uses none of it. With replicas it counts in `used_memory` and against `maxmemory`: on a master with a small `maxmemory` (tens of megabytes), set it back to `1mb`. Under heavier writes, or for replicas that are away longer, give it a few seconds of writes.
- **A transaction that names a key a `MIGRATE` is moving gets `-TRYAGAIN`,** as a multi-key command does in Redis during a reshard. Single commands wait for the move instead. Clients retry `TRYAGAIN`.
- **A full sync can hold up to 1 GiB more on the master** while the replica loads (`repl-replica-sync-max-backlog-bytes`), and that memory is not counted against `maxmemory`. Lower it on a master close to its memory limit.
- **Replicas stand for election only when they are in step,** as in Redis: one restarted while its master is down no longer takes over (unless `cluster-replica-validity-factor` is 0), and one in the middle of a full sync never does.
- **One server per data directory.** A server takes a lock on `kividb.lock` in its directory before it reads anything there. A second one started in the same directory waits until the first exits, and says so in its log every 5 seconds. Give each server its own directory.
- **A manual failover that cannot complete pauses writes for up to 10 seconds,** as in Redis. Before, the pause was 5 seconds, and writes could be lost.
- **Replicas with `tls-replication yes` tell their master their TLS port,** as Redis does, even when they also have a plaintext port.

## Known issues

- **AOF: a power loss during a checkpoint can leave a gap in the log ([#277](https://github.com/kividbio/kividb/issues/277)).** A checkpoint turns the log over: it syncs the old log while new writes go to the new one. The kernel may get part of the new log to the disk before the end of the old one. A power loss inside that window, which lasts up to a few seconds on a slow disk, can keep the newest writes while losing the last ones before the checkpoint, where recovery should stop at a clean cut. A process that is killed or crashes, `SHUTDOWN` and a restart lose nothing: only a power loss or a kernel crash is affected. In 1.1.x, the same window stalled writes instead.
- **Memory freed by dropping a large vector index stays with the process.** After `FT.DROPINDEX` and deleting its documents (a million 1536-dimension vectors in [the vector benchmark](https://github.com/kividbio/kividb/blob/v1.2.0/benchmarks/1.2.0/vector/README.md)), `used_memory` falls at once but the resident size stays where it was, until `MEMORY PURGE`, which gives it back in under a second. Memory limits in containers count it until then.
- **`redis-cli --cluster reshard` under heavy writes slows the source node's writes to seconds ([#310](https://github.com/kividbio/kividb/issues/310)).** `CLUSTER GETKEYSINSLOT`, which redis-cli calls for every slot, and `CLUSTER SETSLOT … NODE` walk the whole keyspace ([#294](https://github.com/kividbio/kividb/issues/294)), so a 128-slot reshard of a node with 2M keys took 12-27 minutes under 100k writes a second. Meanwhile write p99 on that node rose to about a second with `--io-model uring` (100 ms with `tokio`). No write was lost, and every reshard finished. 1.1.x and the earlier 1.2.0 release candidates did the same. `CLUSTER MIGRATION IMPORT`, which the Kubernetes operator uses, isn't affected: reshard with it, or run `redis-cli` resharding when writes are light.
- **`WAIT` on an io_uring server answers `0` too early under concurrency.** With 16 clients each doing a write and `WAIT 1 200`, about a fifth of the `WAIT`s returned `0` after 200-400 ms although the replica had the write, and the server did about 200 such pairs a second, against 6,000 with `--io-model tokio`. No write is lost: the replica has them. 1.1.x does the same. Until it is fixed, a server that relies on `WAIT` can run with `--io-model tokio`.## Benchmarks
